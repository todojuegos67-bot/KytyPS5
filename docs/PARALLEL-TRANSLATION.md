# 并行翻译 guest 命令缓冲（设计，2026-10-05 起）

目标：像原生 PC 引擎多线程录制命令列表那样，让多个线程同时翻译 guest 的图形命令缓冲（DCB），
把"单个渲染线程翻译整帧"这条串行瓶颈拆开。1-1 行走时预期帧时间 23 ms → 约 17 ms。

## 1. 为什么是这里（10-05 实测，1-1 行走，表模式）

- 一帧约 23 ms：渲染线程忙 21.4 ms（图形队列 q0 16.5–17 ms，剔除队列 q49 3.2 ms，其余异步 1.7 ms），GPU 忙 14.2 ms。
- 翻转后逐毫秒（scratchpad chain/bins 分析）：
  - 0–6 ms：GPU 91–96% 忙（上一帧收尾 + 剔除），渲染线程翻译 q49；约 9 个游戏 job 线程全在等 GPU 读回。
  - **8–16 ms：渲染线程 100% 翻译主批次，GPU 只有 13–38% 忙**；命令缓冲交给驱动后 0.1 ms 内就开始执行
    （GPU 在等翻译，录制线程延迟中位 14–39 µs）。
  - 16–25 ms：GPU 追上来执行主批次。
- q0 每帧约 23 个命令缓冲，耗时集中在少数大 pass：4 个 38–43K dword 的（各 3–4.5 ms，翻转后 13–16 ms 先后开始）
  合计约 6.8 ms，帧尾 12K dword 的后处理 2 ms。
- 命令缓冲之间几乎不靠寄存器状态传递：所有图形 DCB 的 SET_CONTEXT_REG 直写为 0，上下文状态按 draw 由
  SET_CONTEXT_REG_INDIRECT 从内存块加载；每个 DCB 以 SET_UCONFIG 0x342 + WAIT_REG_MEM 开头。
- 模拟（subs3.py，按实测提交时间与每个 DCB 的翻译耗时排程）：2 个线程按 DCB 并行，q0 的帧内跨度 -5.7 ms；
  3 个以上 -6.5 ms（此后受游戏自己的提交时间线限制）。因果探针此前测得 q0 翻译的帧时间斜率约 1。

## 2. 9 月 26 日的两线程拆分为什么没成（docs/RENDER-SPLIT-NOTES.md，分支 experiment/render-split-wip-20260926）

那次是"前端遍历 PM4 + 预算程序/SRT，后端按序执行"，粒度是单个 draw/dispatch：
- 交接每项 0.3–1 µs，而每项工作只有 1–5 µs；程序缓存互斥锁争用约 1.5 ms/帧；约 320 次/帧准备因读到
  GPU 监视页而作废。
- 帧链效应：后端更早结束 → GPU 队列更深 → 帧中读回变慢、帧首链变长，抵消收益。

本设计的不同：粒度是整个 DCB（每帧约 23 个，交接开销可忽略）；工作线程各自录制自己的 Vulkan 命令缓冲
（不经共享的单生产者流）；按 guest 顺序提交。

## 3. 架构：投机翻译 + 按序提交

- 按序线程（现在的渲染线程）照旧按 guest 顺序处理所有队列，并负责提交。
- 工作线程从已入队、尚未处理的 q0 DCB 中取一个，**投机**翻译到它私有的命令缓冲：
  - 寄存器状态：DCB 起始状态 = 复位状态（上面实测 DCB 自带状态；首个 DCB 的 CLEAR_STATE/复位单独处理）。
  - CP 副作用（WRITE_DATA、EOP 标签、DMA、线性拷贝等对 guest 内存的写）：不执行，记入私有覆盖层；
    本 DCB 后续读取先查覆盖层（沿用 WIP 分支的 PendingWrite/FrontReads 思路）。提交时按序执行。
  - 缓存：只读查询；需要修改共享状态的操作（注册新缓冲、创建图像、首次 store 变体等）→ 放弃投机，
    这个 DCB 轮到时由按序线程照常翻译。可推迟的修改（LRU 触碰、每帧集合校验标记、需要上传的脏数据）
    记录下来，提交时按序应用。
  - 图像布局：记录每个图像的入口布局假设与出口布局；提交时与真实布局比较，不符就在私有命令缓冲前
    插一个修正屏障的序言。
- 按序线程轮到一个已投机完成的 DCB 时：校验（翻译期间按序线程执行过的 CP 写是否与它读过的范围重叠、
  缓存注册纪元、布局假设），通过则执行记录下来的副作用与推迟的修改、提交它的命令缓冲；不通过则丢弃，照常翻译。

## 4. 需要改的基础设施（10-05 代码梳理结论）

1. 录制与提交（vulkan-recording、CommandScheduler）
   - 现在每个生产者线程有自己的流和自己的 Kyty.Record 工作线程，流之间无序；tick 在生产者上分配
     （"只有本线程分配 tick"）；只有一个当前命令缓冲 m_command、一个命令池。
   - 改为：每个工作线程自己的命令池/当前命令缓冲/流；tick 在提交时按 guest 顺序分配；一个按 tick 顺序的提交者。
     翻译期间需要"当前 tick"的地方（StreamBuffer 监视、DeferOperation、描述符堆、池标签、读回）要改成
     提交时补齐或线程私有。
   - 工作线程不得等待 GPU（避免等一个排在自己之前、尚未提交的 tick 而死锁）：环形缓冲按线程分配、足够大，
     需要等待就放弃投机。
2. 屏障与渲染通道
   - 渲染通道不跨 DCB（现在每个 DCB 结束都会 EndRendering），可直接按线程。
   - 全局 last_work、dispatch 批计数、Image 的 transit group 改为线程私有；"guest 重复写不加屏障"不能跨线程边界。
   - 图像布局按上节在提交时修正。
3. 缓存
   - 现在靠"单 GPU 线程"加一把 RenderContext::m_mutex（每个 draw/dispatch/native try/table continue 都拿，
     等于全局锁）；绘制与 dispatch 各有一个 RenderExecutor，各有自己的 XPR/表缓存。
   - BufferCache 无锁（ObtainBuffer 每次：读回排空、LRU 触碰、UploadDirtyRanges 往 Current() 录拷贝；
     未命中改缓冲表/页表/BDA 页表/注册纪元）；MemoryTracker/PageManager 已按区域自旋锁并发安全；
     TextureCache 有自旋锁但 LRU、slot 直接访问、Image::binding、布局状态都不在锁内；
     PipelineCache 一把粗锁包住 MaterializeResources 与同步编译，"上一次调用"的输出
     （table_pending/table_waiting/m_pipeline_waiting）在锁外读——多线程会竞争。
   - 表/native 缓存每帧都在写：pair/dispatch 表查即插、图像集 used/validated_frame 每次写且会被删除
     （别的线程持有的指针会悬空）、解析过的 V# 缓存命中也刷新、native 记录每次使用都改。
   - 结论：最难的是"单一 GPU 时间线"（一个命令缓冲与 tick 流、布局、缓冲 GPU 归属、按 CurrentTick 回收的
     环与池、guest 跨队列标签等待）——这是重新设计，不是加锁能解决的。投机线程用自己的执行器
     （表/native 缓存各约 4 MiB、各自预热），共享缓存只读查询，结构性修改即放弃。
   - 区域同步（BDA 读的脏数据上传，每帧约 900 次）几乎每个 DCB 都有：必须做成"可推迟"
     （提交时按序上传到该 DCB 命令缓冲之前的序言里），否则投机几乎全部放弃。
   - 顺带发现并已修：计算执行器的表模式 dispatch 退役的描述符集从不回收（只有绘制路径调用 NativeXprCollect），
     池每 1024 个集合新建一个，长时间游玩持续增长。
4. guest 侧
   - GuestGpu 一次处理一个提交、按帧纪元门控；投机不改变 guest 可见顺序：标签、读回、映射变化都由按序线程按序处理。

## 5. 分阶段

1. 基础设施：线程私有命令缓冲/池/流 + 按序提交与 tick 分配（1 个工作线程、投机全部放弃时与现在等价）。
2. 投机翻译一个 DCB（只读缓存 + 覆盖层 + 放弃），校验模式：投机结果与按序翻译逐命令比较。
3. 提交路径：副作用、推迟的修改、布局序言；先 1 个工作线程，再多个。
4. 减少放弃：常见修改改为可推迟；按放弃原因计数逐个处理。
5. 每阶段：同进程 A/B、1-1 行走/翻滚、13 世界巡检、截图比较。

## 6. 实现现状（10-06，同线程 M1b，KYTY_SPECULATE=1，src/graphics/guest_gpu/speculation.cpp）

- 段 + 洞：投机翻译不了的 draw/dispatch/EOP 成为"洞"，记下 CP 状态快照，提交时在前后两段之间按序翻译；
  其他拒绝就停止，余下按序。每段提交前：Changed()（缓冲范围的注册纪元、图像仍解析到同一对象、映射纪元）、
  元数据事实（未清除的仍未清除）、干净读与洞的写/退役集合不冲突；Before（上传、BDA 准备、图像恢复到段入口
  布局）→ SubmitRecorded → After（CP 写日志、拷贝反馈、LRU、图像出口布局）→ 下一个洞。
- 预测：计算清除（m_meta_clears，按着色器 + user data）的洞之后，目标视为已清除，消费它的 draw 成为洞。
- **等待**：投机遇到未满足的 WAIT_REG_MEM 就停止（不做洞）——guest 在标签之前写的内存是给标签之后的命令的
  （bdaDirtyRegions.h 的模型）。按序翻译停在等待处；提交刚好满足了它（标签多由本 DCB 的 EOP 洞写）或挂起后恢复时，
  从等待处重新开始一次投机（CommandProcessor::AtWait）。可恢复的"等待洞"已删除。
- **CP 写日志覆盖读**：投机期间 CPU 侧的读（SRT 求值、CP 读）要看到本 DCB 尚未执行的 CP 写——值写取日志值，
  拷贝从源地址读（State::ReadJournaled）；自己 GPU 工作写的范围、被收回的写（洞的）则拒绝。10-06 的"世界全黑"
  就是 SRT 读到了一次 DMA 拷贝之前的常量（深度预通道顶点常量），预通道深度错误，G-buffer 的深度相等测试全部失败。
- 1-1 行走（每帧）：q0 约 22 ms，保留的投机翻译约 13 ms，丢弃约 0.1 ms，提交 0.9 ms + 洞 3.5 ms；同线程时
  只有开销（28–38 fps，按序约 45）。下一步：降低洞（DRAW_INDEX_INDIRECT_MULTI、写图像的 dispatch、EOP 提交），
  再做线程安全与工作线程（阶段 3）。

## 7. M2（工作线程）计划

主线程（GPU 线程）只做：提交（校验 + Before/After + 洞）、停止处之后的按序翻译、其他队列。按 1-1 的数字，
q0 在主线程上从约 16 ms 降到约 9 ms（提交 0.9 + 洞 3.5 + 按序余下 4.5）。

1. 拆分：Speculation 的"翻译"产出一个结果对象（State、洞与 CP 快照、录好的命令缓冲、环上的分配、起始/结束
   CP 状态、翻译时间），"提交"消费它。先同线程、行为不变。
2. 在工作线程上翻译（主线程先同步等它）：线程本地（t_state、recorder、录制流 ProducerScope + Drain）、
   IsGpuThread 的 15 处检查改为"翻译线程"语义、每个工作线程自己的 CP/执行器/上传环。
3. 链式投机：工作线程按 q0 顺序跑在主线程前面；DCB k+1 从 DCB k 的投机结束状态开始，提交时与真实起始
   CP 状态逐字段比较；它的读还要叠加 k 尚未提交的日志、拒绝 k 的 GPU 写范围。
4. 效果日志：主线程上所有在投机开始之后、提交之前发生的写（其他队列的 GPU 写、CP 写/拷贝、洞、退役的
   描述符集）进一个带序号的日志，提交时与投机的干净读比较（取代现在只在洞里捕获的 t_effects）。
5. 线程安全：表目录（pair/variant/记录）由按序路径写、投机只读 → 读写锁或不可变快照；每次绘制都改的部分
   （resolved V#、held 缓冲、图像集 used 标记、emit 状态）改为执行器私有；缓冲/纹理缓存的结构修改
   （注册、合并、删除）与投机读之间用世界锁或延迟回收；图像子资源状态读写加每图像锁。

10-06 共享状态普查（只读子代理）要点：
- 投机今天与按序 q0 共用执行器，并会写其中的共享部分：pairs 插入（被拒的包也插）、TableReset（退役集合、改写
  pair）、每秒一次的图像集清扫（会删掉别处持有的 TableImageSet）、TableValidateSet 的帧标记、resolved V# 缓存、
  held 缓冲、emit/last_*、NativeXprCollect（删记录、vkFreeDescriptorSets，池需要外部同步）。pair/variant/状态/
  管线只由按序 TableStore 创建 → 投机必须读共享目录；清扫、Reset、Collect 在投机中应拒绝或推迟。
- BufferCache 索引无锁：页表桶惰性创建（非原子 unique_ptr）、SlotVector 是 deque（insert 可能重分配映射、
  erase 原地析构 → 投机拿到的 Buffer* 与 HeldBuffer 会悬空）、注册纪元与区域注册向量是普通变量；
  DMA_DATA、AdvanceFrame 的 GC、ProcessFaultBuffer 都在 RenderContext 锁外修改。
- TextureCache：m_slot_images 不加锁读；SpeculativeEntry 无锁复制 backing.subresource_states，而按序
  GetBarriers 会 resize/clear 它（释放后使用）。LRU 触碰推迟到提交 → 提交前的 GC 可能回收只被投机用到的图像。
- 线程身份：工作线程上 IsGpuThread 为假，内存读取路径会回退到普通 memcpy；读故障在工作线程上会
  SendCommandSync 到 GPU 线程——GPU 线程若在等工作线程就死锁 → 工作线程遇到被监视页应拒绝而不是读。
- 录制：每个在途投机一个 Recorder（命令池）；延迟提交时工作线程提交前必须 Drain 自己的流；Finish 按
  PendingTick 统一解析两个环和两个执行器的退役集合 → 两个重叠的投机不能共用一个 Speculation 对象。
- 提交只检查洞的效果：翻译与提交之间其他按序工作（其他队列、上一个命令缓冲）的写没有检查 → 效果日志。
- RenderContext::GetMutex 是递归临界区，投机在每次表绘制/dispatch 都拿；按序的 DMA_DATA、EndSubmission/
  AdvanceFrame、ProcessCommands、Speculation::After 不拿。

10-06 早上测量（1-1 行走，按序，临时诊断 KYTY_DIAG_M2，已删除）：
- 积压：GPU 线程开始一个 q0 DCB 时，队列里平均还有 6–7 个图形 DCB；提交到开始平均 3.6–4.1 ms（65–75% 超过
  1 ms）。工作线程有足够的提前量。
- 等待：每个 DCB 都以等待开头，平均约 11 个顶层 WAIT_REG_MEM。提交那一刻已满足 21%；之后由本 DCB 自己的 CP
  写满足 66%（投机的日志覆盖能看到）；由更早的图形 DCB 写 5%（总是往前 2 个或 4 个以上，从不是紧邻的前一个）；
  由计算队列写 8–10%（写标签的计算 DCB 总是先于这个图形 DCB 提交）；**CPU 写的标签 0**。按序也阻塞的等待约 80/1000 DCB。
- 按"最坏的等待"分 DCB 的翻译时间：提交时即满足 7%、本 DCB 写 24%、更早图形 DCB 15%、计算队列 45%。
  有阻塞等待（更早 DCB 或计算队列）的 DCB 约 55%，第一个阻塞等待在其 15–28% 的 dword 处，但只占其翻译时间的 5–9%。
- 结论：遇到等待就停的工作线程只能提前做约 1/3 的 q0。要拿到大头，投机必须越过等待（段边界放在等待处，提交时
  按序等待它满足，挂起/恢复提交），并用全局效果日志校验其间其他队列/更早 DCB 的写。CPU 依赖的数据都在该 DCB
  提交之前写好（标签的写者都已提交在前、CPU 不写标签），所以在提交（Enqueue）之后开始的投机看得到它需要的 CPU 写；
  一般情况下的保险：提交时对干净读做内容校验（哈希）。

## 8. M2 实现与测量（10-06 上午）

已实现（默认关，KYTY_SPECULATE）：
- 1：同线程投机 + 提交（M1b）；3：同线程"提前翻译"——一个 DCB 开始时把队列里排着的后续 DCB 都按链翻译好
  （每个从前一个的投机结束状态开始，读能看到前一个未提交的 CP 写：链式日志、合并的链集合、图像状态、清除预测），
  提交时用 SameState 校验起始状态；4：工作线程在 DCB 提交（Enqueue）时就开始翻译，GPU 线程提交结果。
- 执行器拆分：投机执行器读 GPU 线程执行器学到的"目录"（table pair/dispatch、image set、draw state、计算清除、
  线性拷贝着色器），按角色分开的证明字段；目录在所有者写时独占锁、投机线程读时共享锁。
- 结果对象（Result）：每个在途的翻译有自己的 recorder、pending tick（PendingTick+序号）、起止 CP 状态；
  环上的分配按 pending tick 分别释放。
- 等待洞（v2）：投机遇到未满足的 WAIT_REG_MEM（标签由 CP 写过的地址）不再停止，作为洞；提交时按序执行，
  未满足就挂起提交（Outcome::Blocked），提交在该 submission 恢复时继续（Resume）。CPU 写的标签仍停止。
  WAIT_FLIP_DONE、FLIP、GET_LOD_STATS 也作为洞。
- 全局效果日志（EffectsLog）：GPU 线程的所有工作（按序翻译、洞、提交自己的写、其他队列）记录 GPU 写、CPU 写、
  退役的描述符集；每个结果从它开始翻译时的位置起校验干净读、拷贝范围、退役集合；链读按内容校验；满足的等待在
  提交时重新测试；内存检查改为"段用过的范围被 unmap 过"（UnmappedSince），不再看全局映射纪元。
- 并发：SlotVector 改为不搬动的分块存储 + 原子 generation/alive；缓冲注册纪元原子、按区域纪元表固定大小；
  删除的缓冲/图像在投机线程当前包结束后才销毁（包计数器 g_packet）；图像屏障状态有每图像自旋锁；
  GPU-dirty 精确区间有读写锁；投机线程直接录制 Vulkan（无录制流）、不拿渲染互斥锁；GPU 线程不再自己投机。

1-1 行走测量：
- 模式 3（同线程）：约 85–90% 的 DCB 整体提交，丢弃的翻译约 0.1–2 ms/帧（等待洞之前）。
- 模式 4（工作线程，GPU 线程只在结果已在翻译中时等它，否则自己按序做）：28.6 fps（模式 0 为 45.8）。
  工作线程的投机翻译已和按序一样快（保留 14.3 ms/帧 + 洞在 GPU 线程上约 2 ms ≈ 按序 q0 16 ms），
  但丢弃约 5.7–7.3 ms/帧，提交约 2.5 ms。GPU 线程到达一个 DCB 时，约 63% 的情况工作线程正在翻译它（等），
  即"随到随翻"：没有积压可以提前做。结论：**单个工作线程不可能快过按序**（同样的翻译量，只多了提交）；
  收益必须来自多个工作线程并行翻译不同的 DCB。
- 起始状态可预测性（按序运行测）：DCB 起始的完整 CP 状态与上一帧同位置 DCB、或与上一个 DCB 的起始状态相同
  只有约 4%（绘制层面的字段 98–99% 相同）。所以并行工作线程不能用"猜"的起始状态，需要精确的链：
  方案是一个只处理状态的快速遍历（寄存器、索引/间接基址、实例数等，不翻译绘制），先算出每个 DCB 的起始状态，
  再把 DCB 分给多个工作线程。

## 9. 多工作线程（10-06 上午，KYTY_SPECULATE=4，KYTY_SPECULATE_THREADS=N）

- 状态遍历（state pass）：一个线程按序只跑改变 CP 状态的包，给每个 DCB 精确的起始状态；N 个工作线程并行翻译
  不同的 DCB，提交时 SameState 校验（"another start state" 在 1-1 为 0）。
- 两线程卡死的根因：结果对象回收。翻译线程在锁内选好 previous（结果 R），解锁后 GPU 线程提交了 R 并把它放回
  该线程的空闲池，Translate 又把 R 取出来当自己的结果 → R.previous = R → Inherit() 死循环。修法：previous 在锁内
  链接（只链接未退役的）；Finish 同时解除 m_ahead 与"正在翻译的结果"（Translator::current）上的链接；
  退役的结果只有在所有正在进行的翻译开始之后退役的才可复用（m_clock / Translator::since / Result::retired，EBR）。
- 表执行器的按角色证明字段（generation、last_set、validated_frame）原来所有工作线程共用角色 1 → 改为每个线程一个角色。
- 坑：TableDispatch 查找失败时不能 Spec::Refuse——调用者在它之后还有线性拷贝的 CPU 路径；拒绝会把拷贝变成洞，
  其日志范围被"收回的写"污染，后面所有读都拒绝（28.8 万个洞，11 fps）。现在由 m_dispatch_declined 带回原因。
- 两个工作线程：33 fps（单线程 28.6，按序 45.8）。工作线程跑在前面（GPU 线程到达时只有约 37% 在等），但每 2000 个
  DCB 约 550–600 个在提交时停止，丢弃约 10 ms/帧，由 GPU 线程按序重做。60% 的 DCB 是"盲"翻译（前一个 DCB 还在
  另一个线程上翻译，没有链），2/3 的停止发生在盲翻译里。
- **状态遍历记录（pass record）**：状态遍历同时把每个 DCB 的 CP 内存写记进一个 Spec::State（WRITE_DATA 的值、
  CP DMA 拷贝/小填充、线性拷贝着色器的拷贝；不能确定的写——时钟、GPU 端拷贝、大填充——记为已写），以及按目录
  预测的计算清除。没有已翻译的前一个结果时，翻译链接到前一个 DCB 的记录；结果提交（Finish）时，链接改指向该 DCB
  的记录，直到 GPU 线程做完它（Done）才断开。通过记录读到的值仍按内容在提交时校验（chain_reads）。
  结果：盲翻译 0，停止从约 600 降到约 200/2000，"处理器写"类停止几乎消失；剩下以"表面已清除"、图像/缓冲注册为主。

## 10. 分块与结论（10-06 下午）

- **分块**：状态遍历每 128 个 draw/dispatch 切一块（不切在一串间接绘制中间），工作线程按（DCB, 块）翻译，GPU 线程
  逐块提交；没有可用结果时只按序翻译到块尾。q0 在 GPU 线程上的时间 18 → 14.5 ms/帧，等待 6.4 → 2.5，丢弃
  7.5 → 1.7，97.7% 的块整块提交。每段一次 vkQueueSubmit（打开的命令缓冲 + 录好的）。
- **8 个工作线程下找到的正确性问题**（都已修）：
  - 表描述符集的 vkUpdateDescriptorSets 原来经录制流延后执行；集合发布后工作线程立即绑定，早于流里的写入
    （VVL "never updated" / THREADING）。TableResolveSet 现在直接写（集合是新的，或在已完成的 tick 退役）。
  - 表绘制的目标：整图布局与目标布局相同时跳过了转换；提交后第 0 层是 COLOR、第 1–3 层是采样布局时，下一个画到
    1–3 层的绘制在错误布局里渲染。现在图像有按子资源的状态时总是转换。
  - 设备丢失后时间线信号量读作 UINT64_MAX，之后的"destroyed while in use"都是症状。新增 src/local/device-fault.h：
    有 VK_EXT_device_fault 时（RTX 5090 有）报告出错地址和覆盖它的 BDA 缓冲（存活/已销毁）。
- **测量**（干净构建，1-1 存档来回走，8 个工作线程）：模式 0 f1 46–47 / b1 50–51 fps；模式 4 f1 38–39 /
  b1 44–47 fps，**约慢 15%**。模式 4 的 GPU 线程工作量和模式 0 几乎一样（19.7 vs 20 ms/帧）：
  - 工作线程只做纯翻译；资源准备（上传、BDA 驻留、图像状态、LRU）在提交时由 GPU 线程做；
  - 洞（约 170/帧：拒绝的 dispatch、清除过的目标、DRAW_INDIRECT、拒绝的组合）在 GPU 线程上冷执行；
  - 延迟：GPU 线程常等工作线程刚拿走的块（render_busy 约 75%）。
- **决定**：模式 4 的代码保留，默认关闭（KYTY_SPECULATE=0；=4 加 KYTY_SPECULATE_THREADS=N 打开）。要赚回来需要
  资源准备也在工作线程上（线程安全的缓冲/图像缓存与上传）、更少的洞、更便宜的逐段提交簿记。图像写 CS 走表路径
  （减少 dispatch 洞）试过两次：它们的存储写让后面的段因"图像已失效"停止，丢的比省的多。
- 单线程上更直接的杠杆（模式 0，1-1 重视角 21.7 ms/帧）：表绘制约 0.9 µs × 约 9200 次（8.4 ms），表 dispatch
  2.7 ms，普通路径的一次性 dispatch 2.6 ms，线性拷贝 1.6 ms，PM4/寄存器 2.7 ms，VirtualProtect 1.3 ms。
